# SAMAVESH: Technical Strategy & Architecture

## Overview
SAMAVESH is an LMS with sign language translation engine. It aims to break down communication barriers by translating written or spoken text into realistic 3D avatar sign language (using the "Luna" avatar). The project supports multiple sign languages—including Indian Sign Language (ISL), Gujarat-Localised ISL (G-ISL), and American Sign Language (ASL)—and is accessible via a web application and a Chrome extension.

## 1. Technology Stack

### Backend Stack
- **Framework**: FastAPI (Python)
- **Server**: Uvicorn (ASGI web server)
- **NLP & Text Processing**: spaCy (for lemmatization, part-of-speech tagging, and syntactic parsing)

### Frontend Stack
- **Core**: Vanilla HTML5, CSS3, and JavaScript (ES6+). The decision to avoid heavy frameworks (like React or Angular) ensures maximum performance, minimal bundle size, and easy embedding into third-party sites.
- **3D Avatar Rendering**: CWASA (JASigning) WebGL engine. It parses SiGML and drives the 3D avatar skeleton.
- **Styling**: Component-based vanilla CSS (`tokens.css`, `components.css`) adhering to modern design aesthetics and high accessibility standards.

### Browser Extension
- **Platform**: Chrome Extension Manifest V3.
- **Architecture**: Injects a sandboxed, draggable, and scrollable UI overlay into the DOM via content scripts, communicating with a background service worker to fetch translations from the SAMAVESH backend.

### Quality Assurance & CI/CD
- **Testing**: Pytest (Backend unit tests), Playwright (E2E browser testing).
- **Accessibility**: Axe-core for rigorous WCAG compliance testing.

## 2. Core Translation Pipeline Strategy

Translating natural language into sign language requires more than just mapping words to gestures. The SAMAVESH pipeline employs a strategic, multi-step heuristic process:

1. **Input Normalization & Routing**: Text is ingested via the web app or extension. If the input language differs from the target sign language's base language (e.g., Gujarati text to ISL), the backend first performs text-to-text machine translation.
2. **NLP Parsing & Tokenization**: `spaCy` analyzes the text, determining the Part-of-Speech (POS) and lemmas. 
3. **Lexical Filtering**: We apply relaxed stopword filtering. While traditional sign language omits many connecting words, our strategy retains certain adpositions (like "about") and demonstratives (like "this") to provide a literal, word-for-word translation experience that users prefer for immediate comprehension.
4. **Gloss Mapping**: Tokens are mapped to "glosses" (the text labels for specific signs). 
5. **SiGML Generation**: The glosses are converted into SiGML (Signing Gesture Markup Language), an XML-based notation describing handshapes, spatial locations, and movements.
6. **Avatar Rendering**: The frontend CWASA engine interprets the SiGML and dynamically animates the Luna avatar in the browser.

## 3. Fallback Strategies & Edge Cases

- **Fingerspelling Fallback**: When a word does not exist in our pre-recorded sign lexicon (e.g., proper nouns, technical jargon), the system falls back to fingerspelling. Crucially, our regex logic (`\p{L}`) natively supports all Unicode letters, allowing seamless fingerspelling for non-Latin scripts like Gujarati or Hindi.

## 4. Key Architectural Decisions

- **Modularity via `luna-translator.js`**: The translation logic and UI are encapsulated into a standalone, reusable JavaScript widget. This allows identical logic to power the main web app, the Chrome extension, and third-party LMS integrations.
- **Stateless Backend**: The FastAPI backend is completely stateless, relying on client-side caching (e.g., `chrome.storage.local` in the extension) to reduce server load and improve response times for repeated translations.
